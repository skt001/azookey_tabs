# ロングプレス候補 設計基準(統合版)

## 1. 位置付け

本資料は、以下3本の設計基準資料の論旨を、en_qwerty/jp_qwerty間で記法・構成を揃えて統合したものである。

- `donotedit/en_qwerty/README-longpress.md`
- `donotedit/en_qwerty/README-longpress-options.md`
- `donotedit/jp_qwerty/README.md`

候補の採否基準・候補集合そのものは変更しない。変更するのは提示の記法・構成のみであり、元資料(`donotedit`以下)が引き続き一次資料である。

対応する統合版データ一覧:

- [en-qwerty-longpress-all.md](en-qwerty-longpress-all.md)
- [jp-qwerty-longpress-all.md](jp-qwerty-longpress-all.md)

## 2. 共通目的

en_qwerty・jp_qwertyのロングプレス候補は、いずれも特定の既存キーボード実装(iOSの現行実装)の再現を正解とせず、基本キーから利用価値のある文字・記号へ直接到達するための小さな候補集合として設計する。採否は、言語で実際に使われる文字、Unicode上の定義・単独コードポイントとしての性質、基本キーとの体系的関係、文化・地域・入力環境上の実用性を根拠とする。

## 3. 両言語共通の基本方針

- 候補は原則としてUnicode上で単独のコードポイントを持つものを基準とする。結合文字の任意の組み合わせを候補生成の単位にしない。
- 不可視文字・制御文字・ゼロ幅文字は対象外とする。
- 候補の採用基準と候補の並び順は分離する。並び順は原則Unicodeコードポイント順とし、実機ロングプレスメニューの物理配置には依存しない。
- 調査段階では候補を広めに収集し、後工程で実用性・重複・用途を確認して整理する。初版は最終形ではなく、整理前の母集団として扱う。
- 実機(iOS等)の現行実装・既存資料は参考情報として扱い、候補集合の母集団にはしない。候補集合確定後の比較用途に限って使用する。

## 4. en_qwerty 固有の方針

- 基本キーはA–Zの26文字。
- 言語側の情報源としてUnicode CLDRのExemplar Charactersを用いる(main exemplarを中心とし、auxiliary exemplarは必要に応じて補助的に参照)。
- 基本キーへの対応は、Unicodeの分解・大文字小文字対応、文字名・注記、正書法上の拡張関係から判断する。音が似ているだけの割り当ては行わない。
- 大文字化はUnicodeの言語依存マッピングを考慮する(例:トルコ語・アゼルバイジャン語のi/İ、ı/I、ドイツ語のß/ẞ)。
- 句読法(¿ ¡)、引用符・アポストロフィ、ハイフン・ダッシュ・マイナス、通貨記号は、A–Zの文字候補とは別カテゴリとして扱う。
- 基本セット(README-longpress.md基準)とオプションセット(README-longpress-options.md基準)を区別し、両者を統合したものを完成候補一覧(all)とする。

## 5. jp_qwerty 固有の方針

- 半角・全角が対応する文字は直接入力候補として扱う。
- 記号は半角・全角対応に加え、キーの意味・読み・用途から自然に連想できる関連記号を候補にできる。
- 日本語ローマ字入力から連想しやすい特殊かな(小書きかな等)は、Unicode上の分類だけに縛らず候補にする。
- 数字は全角数字に加え、漢数字・大字を候補にする(0は「零」「〇」の両方を扱う)。
- 句読点は実キーボード上で `.` `,` と `。` `、` が別キーとして存在するため、片方向ではなく相互に候補とする。
- ローマ数字・半角カナ等、通常のIME変換で入力することが自然なものは直接入力候補から除外する。
- 基本/オプションの区分を設けず、1本の設計資料(README.md)と1本の完成候補一覧(all)で完結する。

## 6. 言語間で意図的に残す差分

### 6.1 基本キー自身を候補に含めるか

- en_qwerty:候補列に基本キー自身(例:`A`)を含めない。英語入力はASCIIの直接入力でありIME変換が介在しないため、含める必要がない。
- jp_qwerty:候補列に基本キー自身を含める(例:`a = a ａ`)。roman2kana方式ではキー入力が通常IME変換の経路に入るため、変換を経由せず直接入力するルートをロングプレス候補として確保している。

この差分は表記の不統一ではなく、入力方式の違いに基づく意図的な設計であり、統合版データでも吸収・統一しない。

### 6.2 資料粒度

- en_qwerty:README×2(基本/オプション)+ データ×3(candidates/options/all)。
- jp_qwerty:README×1 + データ×1(all)。

オプション層を明示的に分離する設計(en)と、1本で完結させる設計(jp)という方針の違いであり、統合版でも無理に一本化しない。

## 7. 統合版データ一覧の記法

元のデータファイルは、見出し・区切り記号の記法がen/jpで異なっていた(en:`## 見出し`/`KEY = 候補`、jp:`【見出し】`/`key : 候補`)。統合版では以下に統一する。

- 見出し:`## 見出し`(Markdown ATX形式)
- キーと候補の区切り:`KEY = 候補 候補 ...`
- 候補の内容・順序・言語ごとの節構成は変更しない

## 8. 本資料が解決しないこと

本資料は記法の統一のみを目的とし、候補の採否判断・候補の増減は行わない。

例外として、en/jp双方で`¥`キーのみが通貨記号の包括リストを持ち、`$`キーが自身の半角・全角形のみに限定される非対称がen/jp共通のパターンとして確認されたため、指示により修正した。`$`キーの候補を`¥`キーと同一の包括リストに揃え、コードポイント順に並べ直した(どちらのキーからでも同じ通貨記号集合に到達できる)。

JP記号節の`}`キーの候補が`）`(全角右丸括弧)になっていた点は、`｝`(全角右波括弧)の誤りと判断し指示により修正した。

また、JP側が`+`→`±`、`*`→`×`のように意味的に近い記号を追加する方針(本資料5節)を既に採用していることを踏まえ、EN側にも指示により同様の候補`+ = ±`、`* = ×`を追加した(半角・全角の対応ではなく、意味連想による追加)。
